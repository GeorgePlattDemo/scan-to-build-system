## Precedence rule

Human-facing presentation and product intent come from the controlling reference build.

Technical truth and authority come from the accepted repository.

The implementation layer must make those two fit together.

When they do not fit cleanly:

1. preserve the controlling human-facing copy/drawing/order;
2. preserve the repository safety/authority boundary;
3. expose the technical condition as unresolved, blocked, reference-only, or otherwise truthful;
4. do not invent an answer;
5. do not silently rewrite the human-facing source to make implementation easier;
6. stop for George if a real product decision is required.

## Project-door rule

The project icons are functional navigation and product/capability contracts, not decoration.

Each door must preserve:

- its drawing;
- its label;
- its order in the ribbon;
- its human problem / utility;
- the work behind the door;
- its current capability status;
- its developer-context rail;
- regression coverage proving that the picture reaches the intended work.

A door is not restored merely because its picture appears.

**THE PICTURE IS THE DOOR.**

## Current intended progression

The controlling reference establishes an expanding capability story:

1. `Start your own` — open intake / bring what you have.
2. `Critical fit` — the simple alcove / shelf-insert bounded-project proof and configurator.
3. `Space utilization` — the window-seat bounded project that intentionally pushes the present envelope and makes mixed-family / qualified-resolution / unresolved boundaries visible.
4. `Outdoor build` — picnic-table expansion showing reuse, form versus fulfillment scope, and bounded family growth.

Current accepted repository capability such as D-001 dimensional work, rectangular sheet work, and the centered arched S-001 project must be preserved and re-exposed coherently rather than discarded. Their human-facing placement is a product decision to be made deliberately, not opportunistically during unrelated fixes.

## Change protocol

Every future change on or after this stabilization line follows this sequence:

1. State the exact accepted baseline SHA.
2. State the one requested change in one sentence.
3. State what must remain unchanged.
4. Identify the smallest files that should change.
5. Make no opportunistic cleanup, redesign, renaming, routing change, or adjacent simplification.
6. Preserve all controlling copy, imagery, page order, routes, and project-door semantics outside the requested change.
7. Run targeted tests for the requested change.
8. Run regression tests for all previously accepted human paths and load-bearing technical boundaries.
9. Report exact changed files and exact visible behavior changed.
10. Do not promote the result to the next accepted baseline until George reviews the visible application.

If a requested one-line change actually requires broader architecture work, STOP and explain why before making that broader change.

## Stabilization discipline

During this pass:

- one stabilization branch only;
- small coherent commits;
- no stacked feature branches;
- no capability expansion merely because it is convenient;
- no deletion of old work merely because it is currently hidden;
- recovery branches and donor HTML are evidence, not merge targets;
- current `main` technical logic is salvaged wherever sound;
- presentation is rebuilt to the controlling reference instead of forcing the reference to fit accidental current UI structure.

## Acceptance standard

The stabilization pass is not complete until a cold user can visibly walk the intended application and a cold developer can understand why each screen exists.

At minimum the acceptance suite must protect:

- landing copy and order;
- all three starting contexts converging correctly;
- real Page 1 with the four controlling project doors and explanatory field copy;
- gray BUILD GUIDE rail and README pill;
- Back navigation after the home screen;
- Start Your Own / Bring What You Have path;
- Critical Fit / alcove path and configurator;
- Space Utilization / window-seat path, including truthful current boundaries;
- Outdoor Build / picnic path and configurator;
- review / confirmation separation from commercial and production authority;
- current D-001, sheet, S-001, Store, record, and safety boundaries;
- no regression in durable project history / export / import / reopen behavior.
