# User Intake Candidate Facts 0.1

**Status:** candidate branch facts only  
**Branch:** `build/app-intake-authority-0.1`  
**Does not replace:** `CURRENT-FACTS.md` until promoted

In addition to the accepted application facts, this candidate branch now presents:

- the landing proposition with plain-language detail under each existing sequence step;
- an explicit open-door intake contract: broad receipt, source preservation, visible unresolved conditions, no authority promotion from reading;
- the three actor orientations as different starting contexts, not different truth models;
- Page 1 as two paths into one application: mapped project or Start Your Own;
- an interactive **BRING WHAT YOU HAVE** launcher that routes ordinary-language starts into the existing bounded intake children rather than creating a second intake engine;
- nine launcher starts including Pick a Board, plain-language need, measurements, photo/sketch, scan, drawing/PDF, takeoff/cut list, CAD/BIM/structured file, and “I’m not sure”;
- minimum-necessary guidance: do not send unrelated client lists, pricing, workforce data, or other information the project does not need;
- clear current-versus-planned status on the launcher for measurements, photos/sketches, drawing/PDF, takeoff/cut list, scan, and CAD/BIM/structured-file paths;
- Page 2 with visible source / observation-candidate / unresolved seams;
- a two-axis explanation separating provenance from authority;
- a working next-question prompt based on currently visible gaps;
- an explicit conflict rule, while stating that arbitrary cross-source conflict detection is not implemented;
- Store boundary language that keeps Store support separate from production release and Cycle Start;
- confirmation language that freezes one identified version without collapsing order/payment/allocation/release/readiness/fabrication;
- a planned qualified-person loop shown as HOLDER | RULE | QUALIFIED PERSON;
- a future transaction / production / fulfillment narrative explicitly labeled architecture, not a live order;
- linked definition, commercial, payment, fulfillment, and machine domains presented as separate status families rather than one giant status;
- an eight-stage responsibility map from YOU through OWNER RECORD with OWNS / RECEIVES / MAY DO / MAY NOT boundaries;
- an eleven-item non-equivalence list including qualified resolution ≠ production release and machine readiness ≠ Cycle Start;
- owner-record language that refuses to infer missing physical events.

The qualified-person UI is explanatory only. It does not route a question, validate standing, write a `QualifiedResolution`, block confirmation by class, start an expiry clock, or release work.

The commercial / production / fulfillment chain is explanatory only. This branch does not implement an offer, payment, inventory commitment, production release, machine admission/readiness, Cycle Start, physical fabrication, inspection, staging, pickup, or delivery.

The new narrative/open-door/future-chain layers change presentation and navigation into existing intake children only. Existing domain records, Store integration, candidate revisions, review records, and owner archives remain the underlying implemented mechanisms.

Full application suites are still **NOT RUN** for this branch.
