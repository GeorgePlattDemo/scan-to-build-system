## Preserve exactly in meaning

Do not collapse or weaken these distinctions:

- source evidence ≠ observation;
- observation ≠ verification;
- read/extracted ≠ controlling;
- candidate mapping ≠ confirmation;
- confirmation ≠ order;
- order ≠ payment;
- payment ≠ material allocation;
- material allocation ≠ production release;
- production release ≠ machine readiness;
- machine readiness ≠ Cycle Start;
- Store support ≠ Cycle Start;
- qualified resolution ≠ release;
- machine completion ≠ inspection;
- inspection ≠ staging;
- staging ≠ pickup;
- owner record ≠ production packet;
- software result ≠ physical outcome truth.

The project originates with the holder. Downstream authority gets narrower, not broader.

## Preserve the central proposition

The user's confirmed definition should be able to reach downstream work without being silently redrawn, retyped, substituted, rounded, or reinterpreted to make the job fit.

Do not turn that proposition into a claim that every input file can be interpreted or every project can be fabricated.

## Preserve broad intake, narrow commitment

The public promise should remain approximately:

> Bring what you have. We preserve the source, use what we can reliably establish, tell you what we cannot, ask for what is still missing, and nothing becomes controlling just because software read it.

A homeowner and a professional are different starting conditions, not different truth systems.

## Qualified-person loop

Keep the human-in-the-loop bounded:

```text
HOLDER | RULE | QUALIFIED PERSON
```

A qualified person answers one bounded question with named standing, scope, and void conditions. They do not edit the project, issue production release, establish machine readiness, or authorize Cycle Start.

The current app presentation is explanatory only. Do not rewrite it as if routing/persistence/standing validation already exists.

## Allowed edits

You may:

- remove repetition;
- shorten prose;
- normalize capitalization;
- improve headings;
- move explanatory copy to a better screen when the architecture remains unchanged;
- replace jargon with plain language;
- align terminology with current repository names;
- distinguish current/implemented from planned/reference more clearly;
- identify stale statements and propose exact replacements;
- suggest which narrative-layer elements should graduate into first-class UI after verification.

## Not allowed

Do not:

- redesign domain models;
- invent new Store capability;
- invent legal terms;
- invent payment behavior;
- invent file parsing;
- claim OCR/CAD/BIM/scan interpretation that does not exist;
- treat a model/AI parser as project authority;
- add machine-control behavior;
- generate G-code;
- add remote Cycle Start;
- broaden envelopes to make examples pass;
- silently change current runtime semantics;
- remove unresolved states just to make the journey look complete.

## Required output

Produce one bounded report with:

1. **Contradictions** — exact file/location and why the statements cannot both stand.
2. **Stale language** — text that describes an earlier implementation state.
3. **Redundancy** — repeated explanations that can be consolidated.
4. **Terminology normalization** — current preferred term and replacements.
5. **Customer-facing edits** — proposed plain-language copy, preserving meaning.
6. **Professional-facing edits** — remove consumer friction without creating a separate system.
7. **Authority check** — any sentence that accidentally promotes evidence, Store support, resolution, release, readiness, or physical outcome.
8. **Implementation truth check** — anything presented as live that is actually planned/reference-only.
9. **Keep list** — language that is load-bearing and should not be casually rewritten.
10. **Exact implementation handoff** — smallest coherent edit pass after review.

Do not modify files during the audit unless separately instructed.
