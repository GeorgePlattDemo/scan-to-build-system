## Preserve exactly or semantically intact

- source/read/extracted/derived is not authority;
- user confirmation is not order/payment/allocation/release;
- qualified resolution is not release;
- production release is not machine readiness;
- machine readiness is not Cycle Start;
- Store support is not fabrication;
- unresolved means unresolved;
- no silent unit conversion, material substitution, geometry rewrite, conflict resolution, or authority promotion;
- `NO BLOOD ON WOOD`;
- current locked landing proposition unless explicitly authorized otherwise.

The locked landing sequence is a proposition, not a place to inject explanatory prose. Keep the exact public statements clean and move explanation beside or below them. Do not alter the meaning of `YOUR DEFINITION REACHES THE CUT` or turn `YOU CONFIRM` into commercial acceptance, payment, production release, or machine authority.

## Open-door cleanup

The public promise is broad intake, not universal understanding and not unlimited downstream capability.

Keep this meaning intact:

**Start with whatever you have. Preserve what was supplied. Use only what can be reliably established. Show what remains unresolved. Ask for what is still missing. The user confirms the controlling definition.**

Do not create separate intake engines for NEW USER, RETURNING USER, and PROFESSIONAL. They are different starting contexts into one system. A source may be retained even when the current build cannot interpret it. Reading or extracting does not make a value controlling.

## Window-seat edge case — feature it, do not bury it

Use `WINDOW-SEAT-EDGE-CASE-JOURNEY-0.1.md` as the controlling candidate explanation for this story.

The public version should be easy to follow:

**WHAT SHE WANTED → WHY IT STOPPED → WHAT CHANGED → WHAT THE RECORD KEPT**

Preserve the ordered chain:

intent → sketch/photo → drawing with numbers → explicit observations/provenance → candidate configuration → seating use activates additional gates → STOP/refusal when a controlling question is unresolved → review by the appropriate human authority → new configuration version → dependent gates rerun → later Store/capability/commercial/release/execution evidence only if those events actually exist → durable owner record.

Do not collapse this into “the engineer approved it.” Human review must remain question-specific, version-specific, evidence-backed, and authority-bounded.

Do not turn the Project B fixture into a code-compliance claim. `EGRESS_REVIEW_REQUIRED` is a stop/review result, not a declaration of code violation. A revised fixture with no declared AABB intersection proves only that fixture condition; it does not prove jurisdictional compliance or structural adequacy.

The historical Sarah/public demonstration may be used as a clearly labeled story/capability donor showing why a mixed dimensional + sheet job can be decomposed into two fabrication streams. It shall **not** be presented as evidence that the current governed runtime has production authority or that a physical full cell ran the present project. The current governed v0.2 reference remains simulation-only.

Preserve the durable-record payoff in ordinary language: a later replacement request can start from the exact recorded component occurrence/revision/material/outcome basis rather than from re-measuring a damaged part and guessing. But keep the boundary: **reproducible definition is not automatic fabrication authorization; current gates run again.**

## Authority-chain cleanup

Keep the visible chain:

**YOU → STORE → COMMERCIAL → PRODUCTION RELEASE → LOCAL CELL → QUALITY → FULFILLMENT → OWNER RECORD**

The owner begins with the widest authority over what the project is. Downstream actors receive narrower authority, not permission to rewrite the project. OWNER RECORD is a reconciliation layer, not a new actor that can mint authority.

Prefer plain-language distinctions, but do not collapse them. At minimum preserve:

confirmation ≠ order ≠ payment ≠ material allocation ≠ production release ≠ machine readiness ≠ Cycle Start ≠ machine completion ≠ inspection ≠ staging ≠ pickup/custody transfer.

## Known implementation / validation conditions before prose is called clean

The sanitizing pass must not hide a failing behavior test by editing the words around it. If a real behavior contradiction remains, report it separately.

Known classes of pre-sanitize cleanup include:

- retired physical/part occurrence identity must not be silently recycled;
- mapped project projections must remain inspectable on Review without falling through a Board-only renderer;
- landing copy must remain exact rather than being mutated by a narration layer;
- duplicate accessibility/test selectors created by presentation layers should be made unambiguous rather than worked around with misleading copy;
- Store-current browser tests require an exact pinned Store checkout; lack of that checkout is an environment condition, not permission to manufacture a Store answer.

## Deferred Store breadth

The current fake/reference Store catalog breadth may need to increase as richer mapped projects are admitted. **Defer that work from this sanitizing pass.**

Do not invent SKUs, stock, prices, structural suitability, or Store support merely to make the picnic-table or window-seat story look complete. Treat broader catalog coverage as a later Store-owned fixture-expansion task with its own source/basis and tests.

## Desired result

A cold reader should understand the working app without architecture jargon, while a reviewer can still inspect the basis and see every unresolved boundary.

The strongest public story should be simple without being false:

- bring what you have;
- preserve the source;
- make the definition explicit;
- stop when an important question is unresolved;
- route that question to the right authority;
- change the project by revision, not by rewriting history;
- rerun the gates;
- preserve the result so the same component can be identified later;
- let Store, commercial, release, machine, quality, and fulfillment each own only their part.

This is a language/consistency pass. If the pass discovers a real behavior contradiction, report it separately rather than silently fixing behavior while editing copy.
