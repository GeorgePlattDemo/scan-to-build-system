## Window-seat ordering to preserve

A cold reader should be able to follow this without learning the internal architecture first:

1. **What she wanted.** Start with intent. “Bench” or “seat” describes intended use; it is not itself an engineering conclusion.
2. **What she brought.** Keep the sketch/photo, then the drawing with numbers, as separate source records.
3. **What we could establish.** Record attributable observations and candidate configuration without rewriting the originals.
4. **What the intended use changed.** Seating use activates questions about load, span, anchorage, and window/access conditions.
5. **Why it stopped.** A real unresolved gate produces STOP/refusal. The documented edge case uses `EGRESS_REVIEW_REQUIRED`; that is a review condition, not a code-violation declaration.
6. **Who may answer.** Route one bounded question to a person with declared standing for that question. Human review is not a generic APPROVE button and is not production release.
7. **What changed.** The holder changes the project. The correction creates a new configuration/version; it does not erase the stopped version.
8. **What runs again.** Re-run every gate that depends on the changed condition. Closing the access-zone condition does not silently close structural load/span/anchorage questions such as `BLK-U07`.
9. **What may happen later.** Store, commercial, production-release, local-cell, quality, and fulfillment evidence can enter only if those events actually occur.
10. **What the record keeps.** Preserve the intent, sources, observations, exact versions, STOP, review basis, revised definition, repeated gates, and later real outcome evidence.

Load-bearing sentence:

> The first version stopped for a reason. The revised version did not erase the stop. It answered it.

The historical Sarah material may illustrate why one project can decompose into separate dimensional-stock and sheet-stock fabrication streams under one identity. It must remain labeled as historical/capability-donor material. It is not evidence that the current governed runtime physically ran the job; the current governed reference remains simulation-only.

## Durable replacement payoff

The owner record is not paperwork after the fact. It is part of the product value.

If one component fails years later, a replacement request can start from the exact recorded component occurrence, definition revision, material identity actually used, dimensions/features, project version, and available inspection/outcome evidence. The system should not require somebody to begin by re-measuring a damaged part and guessing what it used to be.

That does **not** mean “press reproduce.” The old record supplies an exact starting definition and basis; current Store/capability/safety/release gates still run.

Plain-language boundary:

> Reproducible definition is not automatic fabrication authorization.
