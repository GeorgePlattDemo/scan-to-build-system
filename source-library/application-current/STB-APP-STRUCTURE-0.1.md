## 1. Controlling basis and minimum decision

Read with [STB-APP-BUILD-0.1.md](STB-APP-BUILD-0.1.md), [STB-APP-SOURCE-MAP-0.1.md](STB-APP-SOURCE-MAP-0.1.md), and [STB-APP-STABILIZATION-0.1.md](STB-APP-STABILIZATION-0.1.md) as stabilized at the starting SHA. The source map records the Pass-1 starting baseline; the stabilization report records its corrections. No source is repinned here.

Governed Reference owns project semantics, evidence/verification, gates, packet meaning and authority. Store owns material/stock/capability answers, neutral operation translation, price and fulfillment. Cell owns commissioned local machine truth and lowering. The application owns interaction, permitted candidate calculations and presentation. Candidate Cell objects stay candidate.

The minimum is **one project workspace, two bounded class definitions, one candidate calculation path, and one inspectable project record**. Each class supplies its own questions, attributed relationships and part families. The workspace supplies the common handling of inputs, revisions, rendering, Store questions, confirmations and inspection.

This is not a universal class-authoring platform. It does not need a formula language, generalized constraint solver, plugin marketplace, separate service per role, or a large ProjectClass schema. A class definition may initially combine descriptive data with a small deterministic class-specific derivation function. Class-specific mathematics is necessary; duplicated application state, authority logic and lifecycle handling are not.

**Pass-3 target:** runnable local candidate configuration, consequence propagation, record retention and inspection for both classes. It does not activate Picnic Table governance, transport simulation authority, adopt a Store API, or declare a commissioned machine. Pass-1 R-01–R-04 remain open.

## 4. Revision, confirmation and identity

Keep the following distinctions in the local working record: original declaration; input evidence; selected parameters; class/rule version; derived revision; part occurrences; Store question/answer association; unresolved items; confirmation snapshot; sourced governed records if present. This is the minimum information to preserve, not a field-by-field universal schema.

An edit creates a new candidate revision. Recompute affected derived values and retain their input/rule dependencies. Previous confirmations and Store responses remain historical evidence but are not current for the revised question. A delayed response to an older revision must not overwrite the current disposition. The app cannot extend the validity of a Store response.

Confirmation identifies the exact candidate definition, evidence references, rule version and disclosed unresolved conditions reviewed by the user. It confirms that review only. It does not verify measurements, clear an unresolved item, create a WorkPacket authorization, or convert an old simulation result into a result for the changed project.

Invalid or missing inputs cannot produce NaN, guessed zero dimensions or an apparently valid part. A last valid drawing may be shown only as a clearly marked earlier revision; it must not stand in for the current invalid candidate.

An individual part has a stable occurrence identity within the project and a revision of its definition. Display labels, array positions and geometry hashes are not sufficient identity. Unchanged shelf/leg occurrences retain their identities when another member is inserted or removed. A removed occurrence is retained historically; adding a new occurrence does not reuse its identity. A class switch creates a separate candidate project or explicitly separated class history, not silent reinterpretation of old parts.

Mirrored members are distinct occurrences even if their dimensions match. Features identify their owning occurrence and part-relative location. A replacement inquiry refers to the original project, class version, occurrence and historical part-definition revision. A later physical replacement would be a new physical item, not proof that the old item was fabricated or inspected.

## 6. Classic Picnic Table — structural proof

Recognition here means an application definition is available. It does not mean the Picnic Table has become a governed ProjectTemplate, Project B, approved design or simulation-eligible class.

For Pass 3, a **synthetic geometry test definition** is sufficient and required. It represents candidate dimensional members and hardware/feature relationships for testing reuse. Every test-only range, offset, thickness and relation must be identified as a software-fixture assumption, with a version and expected arithmetic. None becomes an engineering limit, installed capability or construction specification. Do not provide fabrication-release output from this definition.

| Shared step | Picnic Table use | Testable consequence / limit |
| --- | --- | --- |
| Input/configuration | Product length as the first editable parameter; fixture-defined width, heights, repeated-member counts and an explicit illustrative leg layout. | No fictional site measurements are created. Additional adjustable dimensions may wait. |
| Derived members | Repeated tabletop and seat members; two mirrored end-frame leg pairs; transverse members and an explicit hardware/feature relationship. | Shared runner produces individual occurrences, geometry and a candidate BOM from the class function. |
| Length consequence | For a test rule with fixed end overhang e, a longitudinal member length may be L − 2e; tabletop/seat lengths follow their explicitly declared relations to L. | A change ΔL changes the affected member lengths and demand by the expected amount; fixed end-frame leg geometry remains unchanged. This is a declared test relation, not a prescribed real design. |
| Repetition/mirroring | Generate paired end frames at class-derived positions; mirror the specified leg geometry within each end frame. | Mirrored legs have separate stable identities and transformed feature locations; reordering the list does not exchange left/right identity. |
| Angled geometry/features | Represent a fixture leg by declared endpoints, width and thickness, with part-relative hole-center markers and an identified mirrored counterpart. | Endpoint distance and part placement can be calculated (for a planar member, length = sqrt(Δx² + Δy²)); reflection is a declared transform in the class's local project frame. An angled member's orientation alone does not establish its end-cut angles, joinery, drill depth, fastener size or structural adequacy. Those remain separately declared or unresolved. |
| Required operations | Square cutting, a bounded planar angled/miter requirement where expressly specified by the test definition, and drilling requirements tied to declared features. | Keep operation needs separate from the part drawing and Store's neutral sequence. Unspecified cut angle or hole specification remains unresolved. Compound-miter is unsupported in this slice. |
| BOM/material/price | Dimensional wood demand by member dimensions/count; hardware requirement as a separate unresolved line or named test item. | Changes produce a revised Store question. Price is returned evidence or unavailable; no app price model, inferred stock or automatic substitute. |
| Disposition | Class is editable as a candidate while governance, engineering and actual machine support remain unestablished. | Synthetic geometry/range checks never create a governed pass. An available-looking Store example does not establish production eligibility. |
| Replacement | Select one leg from a retained project revision and create a linked candidate inquiry. | Original leg definition and all other occurrences remain unchanged; no order or manufacturing event is created. |

A sufficient numerical proof uses two distinct permitted L values in the software fixture and independently checks that n repeated affected members change total required length by n × ΔL, while fixed leg lengths remain unchanged. A mirrored feature must be located from the same source feature/transform, not from a second unexplained coordinate list. Numeric seeds can be ordinary test data; engineering ranges, load rules and hardware suitability must not be invented to make those tests pass.

**Result:** the same inputs → derivation → components → material questions → disposition → record path supports a product-derived class. Class-specific member relationships change; workspace, confirmation, identity, boundary handling and inspection do not. A second bespoke app is unnecessary.

## 7. Structural proof and stopping rule

The proposal passes the two-class design test if both classes can be represented by §3 and evaluated through §2 with the revision/identity rules in §4. This is a planning conclusion, not executed test evidence.

## 8. Three viewpoints over the same record

The viewpoints are projections of one candidate revision and its source references, not three separately maintained truths.

| Question | User view | Builder / designer view | Participant / auditor view |
| --- | --- | --- | --- |
| What was supplied? | Need, measurements/parameters, source labels and missing items. | Input roles, units, source-to-input mapping and boundary expectations. | Original values, file/source identity, acquisition method/time, status and revision. |
| What was derived? | Named dimensions and parts; visible effect of the last edit. | Class definition/version, dependency relations and allowed derivation function. | Rule identifier/version, exact input revision, results, unresolved dependencies and expected calculation evidence. |
| Why did work stop or continue? | Plain reason, affected part/input and possible next act; distinguish “you may edit” from “this can be made.” | Local input checks versus externally owned Store/governed decisions. | Check provenance, disposition source, evaluation/not-evaluated status, retained prior stop and current limitation. |
| What did Store say? | Material/form/quantity/capability answer; price and fulfillment only when supplied; fixture/stale/unavailable labels. | Semantic question, response binding and handling of missing/stale answers. | Exact requested requirements, respondent/source, response version/time/scope, limitations and freshness basis. |
| What was confirmed? | Readable exact definition and unresolved conditions reviewed. | Snapshot/invalidation rules; no verification side effect. | Confirmation event linked to evidence, class/rule and candidate revision; prior confirmations remain historical. |
| What is the governed status? | Packet/result available for this source, or evaluation/simulation not performed; production unavailable. | Owned record types; no substitute gate logic or app issuer. | Sourced gate results/state, packet identity/version and authority/result references; absence is visible, not silently filled. |
| What survives? | Saved project, individual parts, selected historical revision and linked replacement inquiry. | Identity policy, stable occurrences, feature ownership and local record version. | Revision history, derivation/provenance, output/source correspondence and any missing retained evidence. |
| How was the result produced? | Short explanation of the last change and result. | Same workspace path for both class definitions; required class tests and boundary dependencies. | App build/revision identity, class/rule versions, action/change history, test identifiers and latest available test evidence, including “not run” if absent. |

Audit access must distinguish user-supplied, imported, fixture-supplied, calculated and model-inferred information from verification status. Confidence is diagnostic only. The inspector shows unresolved conditions, Store/capability evidence, any actual GateResult and WorkPacket references, any simulation evidence, `physicalFabricationEligible`, and local versus governed outcome identity.

No auditor must infer a controlling value from pixels. Selecting a visible part and selecting its table row expose the same occurrence/revision. User explanations are sourced from structured results; an architectural code is not the only explanation shown to the user.

A future class designer's entry point is §§2–4 and the new class's tests: supply questions/relations/parts/limitations, register the definition, and exercise the existing workspace. A new gate, Store responsibility or capability must go to its existing owner. Passing a class's arithmetic tests cannot approve those changes.

## 10. Outside-evidence boundary

Preserve a source artifact and its interpretation as separate information. These semantic groups describe a future intake boundary, not a new canonical schema.

| Preserve | Minimum meaning |
| --- | --- |
| Source identity and provenance | Who supplied it, original source if known, acquisition time/method, external revision/date and rights/access context where relevant. Unknown values remain unknown. |
| Artifact identity | File/reference identity, declared/detected type where known, size, hash when computed and hash method. Hash identifies content, not author, calibration or authenticity. |
| Parse/adapter attempt | Adapter/parser identity and version, attempt time/status, source artifact identity, limitations/errors and output references. No parser means “not parsed.” |
| Candidate extraction | Value/unit, feature or document location, extraction method, supporting source region and relevant confidence if reported. Preserve conflicting candidates separately. |
| Knowledge/verification | Supplied/imported/derived/inferred basis distinct from verification; no automatic promotion through a confidence threshold. |
| Project relationship | Which class question or part feature the candidate may address, proposed mapping, unresolved conflicts and any explicit user reconciliation act. |

A future adopted capture adapter must meet the existing governed ObservationSet/Observation contract. A model's inference is not made an Observation by changing its label. The app can retain candidate extraction evidence before any governed handoff exists.

For Pass 3, implement only manual typed inputs and local artifact registration: metadata, optional local content hash, and a link to the relevant question. Image, PDF, sketch, SVG, DXF, phone scan, LiDAR and plan/takeoff **parsing remain absent**. Opening a file records evidence; it does not fill dimensions. An oversized/unreadable artifact or unavailable hash produces an explicit limitation, not fabricated extraction.

Saved drafts may retain metadata/references without embedding file bytes. On reopening, mark unavailable referenced bytes as unavailable and allow reattachment; never imply that missing evidence was retained. Reattaching a different hash is a new artifact/version.

**Successful parsing does not create fabrication truth.**

## 11. Store semantic interface

Ask for the answer, not the database. These are question families for an app-facing boundary, not API adoption, URLs, methods, schemas, candidate Cell interfaces or a pricing implementation.

| App question | Minimum supplied context | Store-owned answer |
| --- | --- | --- |
| Can the material requirement be satisfied? | Required material identity where resolved, unresolved constraints, form, component dimensions/units and quantities. | Match/no match/insufficient information; offered alternative only as a proposed alternative, never silent substitution. |
| Is sufficient usable material represented? | Requested quantity/size and relevant offering reference if already supplied. | Scoped availability/supply route with source and freshness; no inference that on-hand means reserved. |
| Can the required work be supported? | Part-relative geometry/features, required operations, sizes/counts and unresolved operation details. | Declared support/unsupported/unknown, applicable envelope reference/limits and requirements still unmet. |
| What disposition and next act apply? | Current request revision and relevant prior answer. | Store acceptance, defer/refuse or other reported disposition with reasons, limitations and requested next information. |
| What price information is available? | Current resolved requirement and permitted account/context, if applicable. | Attributed price/estimate/quote with its own scope, validity, currency and exclusions, or unavailable. |
| What fulfillment path is represented? | Applicable project requirement and supplied location/context if required. | Reported pickup/delivery/supply option or unresolved answer; no booking or order implied. |

Every response must remain associated with the question and candidate revision it actually answers, its Store/source identity, fixture/live status, time/freshness and limitations. Keep material, stock, capability, commercial and governed results separate. A partial answer cannot imply success for the unanswered questions.

Pass 3 uses a **local test response provider** behind this boundary. It records the actual question and returns only explicitly scoped fixture responses; unmatched or changed requirements receive “no applicable fixture response,” not invented availability. A late or mismatched response is retained for audit but cannot become the current answer. Test fixtures can demonstrate unavailable material, incompatible form, unsupported operations and absent price.

The test provider does not implement Store evaluation, stocking, routing, quotation or reservation. An application-local “no answer” state is not falsely attributed as an official Store refusal or a governed refusal code. `NodeEvaluationResult`, `NodePlan` and `NodeOutcomeRecord` retain their existing meanings when sourced; a semantic question family does not automatically adopt those types as the Store interface. The unmerged Store documentation clarifications from Pass 1 remain clarifications, not a new controlling pin.

### First executable paths

1. Open common orientation; identify the three intended contexts and their actual status. Enter the explicitly local candidate workspace and select User 1 Alcove. This action does not activate COLD/CONTRACTOR or any new governed domain handoff.
2. Supply measurements with sources or deliberately load the published fixture inputs. Configure blank depth/count, see actual arithmetic and linked visual parts, ask the local Store test provider, inspect the disposition, and confirm the exact candidate revision with its unresolved conditions.
3. Save the candidate record, reopen it, change a value, and observe recalculation plus invalidated confirmation/response applicability. The saved object is labeled a local candidate draft, not a released WorkPacket.
4. Select Classic Picnic Table as a separate project through the same workspace. Change length between two declared software-fixture values; observe member geometry, repeated quantities, material demand, selected part features and the revised Store question.
5. Reopen that saved project, select one historical leg definition, and retain a linked replacement inquiry. Keep governance/engineering/capability limitations visible.

RETURNING USER may explain future owner-held continuity; reopening a local draft demonstrates only local retention, not production identity/access management or an activated home-record service. PROFESSIONAL remains a planned explanation; it does not parse a takeoff.

### Reuse versus rebuild

Reuse the guided tour's useful behavior: orientation, visible responsibilities/stops, explicit fixture selection, invalidation on change, unserved-need retention, source labels, inspectable output, reset and self-check visibility. Preserve `NO BLOOD ON WOOD`.

Rebuild the single-person state shape, bespoke shelf-only controls, local “gateResults” export and COLD-only routing as shared candidate handling. Reuse behavior through small extracted helpers where appropriate; do not copy its local checks into a governed gate implementation. Rebuild material/price/capability handling against the semantic boundary rather than the public prototype's heuristics. Native drawings must use derived records, not copied static pictures.

### Pass-3 stop

Stop after the criteria in §14 pass and the bounded code is reviewable. No governed runtime invocation, new/changed GateResult, canonical packet generator, production issuer, Store API adoption, network Store service, stock/price engine, external evidence parser, Cell lowering, controller command, machine animation or physical work. No broader CAD, engineering rule, full Picnic Table construction design or replacement-parts commerce. No automatic merge or deployment follows this planning document.

## 16. NON-AUTHORITATIVE IMPLEMENTATION HINTS

These eight patterns are implementation bearings only, based on the stabilized architecture and general software practice. No product research, library choice, vendor recommendation or dependency is implied.

1. **Declarative class descriptions with bounded derivation functions.** Separate questions/labels from class mathematics while keeping one application workspace.
2. **Deterministic derived-state calculation.** Make geometry, parts and material questions reproducible from identified inputs and rule versions.
3. **Data-driven forms.** Render field roles, units and declared ranges consistently for both classes; form validity remains distinct from governed acceptance.
4. **Component-linked rendering.** A small shared scene/projection model can tie visible members directly to inspectable occurrence identities.
5. **Adapters at owned boundaries.** Keep evidence parsing and Store answers replaceable without moving their authority into the application.
6. **Versioned snapshots with append-only consequential history.** Preserve what the user reviewed and why an earlier response or confirmation ceased to apply.
7. **Stable occurrence identity.** Keep a part's identity separate from its geometry and list position so a replacement inquiry can refer to the right historical definition.
8. **Fixture and negative-path testing.** Test missing evidence, unsupported capability and stale responses alongside valid arithmetic so an attractive rendering cannot conceal an invalid state.
